2. COMO REPRODUCIR (un comando por repositorio)
====================================================================

  BACK                                   FRONT
  cd EntreAulas_Back                     cd EntreAulas_Front
  npm run test:evidencias                npm run test:evidencias

  Genera, en cada repositorio:
    reports/junit/rq1-rq5.xml        Reporte JUnit (un <testcase> por prueba,
                                     con nombre, tiempo y, si falla, el motivo)
    coverage-rq1-rq5/index.html      Cobertura navegable (abrir en el navegador)
    coverage-rq1-rq5/lcov.info       Cobertura para herramientas (Sonar, etc.)
    y la tabla de cobertura en consola.

  Otras ejecuciones:
    npm test                         Suite completa del repositorio
    npm run test:defects             Defectos abiertos (deben fallar)
    npx vitest run src/test/api -t "RQ3.4"   (back) Un solo requisito

  Reproducibilidad:
    - Sin red ni base de datos real: Supabase esta simulado; el JWT es real.
    - Sin dependencia de la hora ni del orden: los tokens usan fechas
      relativas y cada prueba limpia su estado.
    - El script usa --testTimeout=30000 porque bcrypt (12 rondas, ~0,3 s)
      se encola cuando corren muchos archivos en paralelo.

  Como leer el JUnit: cada <testcase name="RQ5·N4: contrasena sin numero ...">
  lleva el ID del caso (P = positivo, N = negativo, C = componente, A = cliente
  API, AX = accesibilidad). Un <failure> dentro del testcase indica el caso
  roto y el mensaje de la asercion. Filtrar por ID: -t "RQ1·N3".

4. COMO UNA REGRESION SE HACE VISIBLE (demostracion real)
====================================================================

Se introdujo a proposito un cambio en el codigo de produccion, se ejecuto la
prueba y se revirtio (el archivo quedo identico: git diff vacio y las suites
volvieron a verde).

  Mutacion 1 (back): auth.routes.ts, POST /create-user devuelve ademas
  "password: user.password" en la respuesta 201.
    Resultado: la API sigue respondiendo 201, pero fallaron 4 pruebas:
      - RQ1·P1 y RQ1·P2:   "Contrato roto: Unrecognized key(s) in object:
                           'password'" (ruta: user)
      - Regresion de contrato "POST /api/auth/create-user 201 (RQ1)":
                           { sobran: [ 'user.password' ], faltan: [] }
      - Seguridad rq1:     "la respuesta no incluye contrasena ni hash"
    Lectura: una fuga de dato sensible que NO cambia el estado HTTP es
    detectada por tres capas distintas.

  Mutacion 2 (front): Login.tsx, se quito disabled={isLoading} del boton.
    Resultado: fallaron 2 pruebas:
      - RQ2·C-P2 (cargando): el boton ya no queda deshabilitado
      - RQ2·C-N1 (anti doble envio): se enviaron varias peticiones de login
    Lectura: se pierde la proteccion contra doble envio y la prueba lo
    detecta sin necesidad de un navegador.

5. POR QUE ESTAS PRUEBAS PERMITEN IDENTIFICAR REGRESIONES
====================================================================

  1. Contrato estricto: un campo de mas o de menos rompe la prueba (en
     especial las fugas de password, hash o token).
  2. Linea base versionada: la huella de claves de cada respuesta esta en
     git; un cambio de contrato exige un commit explicito.
  3. Cada caso positivo tiene su negativo gemelo, con un solo factor distinto.
  4. Las aserciones miran tres cosas: el estado HTTP, el cuerpo exacto y el
     efecto colateral (que se guardo en la base y que NO se llamo).
  5. Los dos lados se verifican entre si: el contrato del back
     (src/test/api del back) y el del cliente (src/test/api del front).
  6. IDs en cada nombre (RQ1·P1, RQ5·N4, RQ2·C-N1...) para filtrar y para
     identificar en el JUnit exactamente que caso se rompio.

====================================================================
7. LIMITACIONES
====================================================================

  - La base de datos esta simulada: se prueba la logica de cada endpoint, no
    las politicas de Supabase ni el esquema real.
  - No se instalo una libreria de accesibilidad automatica (axe). Las
    comprobaciones de accesibilidad son con consultas de Testing Library
    (etiquetas, nombres, roles, foco); cubren lo basico, no todas las reglas
    de WCAG.
  - No hay pruebas E2E en navegador de estos flujos (no se pidieron).
  - La cobertura de api/users.ts y de AdminUsersPage es parcial a proposito:
    editar y desactivar usuarios pertenecen a otro requisito (RQ13).
  - Las pruebas de componentes corren en jsdom: no miden pintura real ni
    estilos.
  - Los casos que dependen de la validacion nativa del navegador (campos
    required o type=email) se afirman con checkValidity(); jsdom implementa
    esa validacion, pero un navegador real puede mostrar el aviso distinto.
